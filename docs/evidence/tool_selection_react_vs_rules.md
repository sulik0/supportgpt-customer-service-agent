# Tool 选择实验：规则路由 vs 受控 ReAct

> 2026-10-27，同一份 100 条 Baseline（SHA256 `1112c040…94cf8a`）、同一套模型配置，只切换 `TOOL_SELECTION_MODE`。
> 原始报告位于 `evaluation/reports/react_compare/`（不进 Git），本文保存摘要。对比脚本：`scripts/compare_tool_selection.py`。

## 实验设置

| 项目 | 值 |
|---|---|
| Resolver / Planner 模型 | DeepSeek（`deepseek-flash`） |
| Analyzer / QA 模型 | `qwen-turbo` |
| ReAct 上限 | 3 步、5 次 Tool 调用、单次回灌结果 600 字符 |
| 可见 Tool | Skill 白名单 ∩ 低风险只读 ∩ 当前角色与意图允许；写 Tool 与高风险 Tool 不暴露 |
| 参数 | Tool 无参数，`customer_id` 由系统绑定 |

| Case Pass Rate | 0.91 | 0.32 | 0.84 |

| HITL Accuracy | 0.91 | 0.93 | 0.92 |
| 平均 Tool 调用 / Case | 2.55 | 1.03 | 2.39 |
| 平均规划步数 | - | 1.57 | 1.08 |

| 端到端平均 / P95 延迟 | 5.30s / 10.96s | 7.54s / 14.04s | 6.93s / 13.59s |

两轮 react 中被拒绝的越权 Tool、被忽略的参数注入、受污染结果和规划失败均为 0；v2 有 1 次重复调用被去重。

## 迭代过程

**v1：所有只读 Tool 都交给模型选择。** 模型倾向最少调用：政策类问题经常一个 Tool 都不查，也常跳过客户画像和历史工单，Required Tool Hit Rate 降到 0.356。客户等级和历史工单决定 SLA 与风险评估，属于风控必需上下文，不应由模型裁量。

**v2：强制上下文 + 模型自选扩展。** 画像和历史工单由系统获取，与规划第一步并行；模型只在订单、账务、物流、服务状态、保修中选择。没有可选 Tool 的 Skill（账户、通用咨询，共 36 条）直接跳过规划，不产生 LLM 调用。提示词增加一条通用原则：涉及客户自身订单、付款、配送、服务或保修时，先核实记录。

## v2 剩余差距

7 条失败都是纯政策问题，例如“v2 政策的退款手续费是多少”“v1 的最长申请期限是多少”。问题没有指向任何订单，模型没有查订单历史；Dataset 要求查询，是因为标注沿用了规则路由的行为。

- 按原标注严格计算：react 0.84，rules 0.91。
- 除去这 7 条标注存疑的 Case，两者在其余 93 条上都是 84/93（0.90）。

本实验没有修改 Dataset。结论是：受控 ReAct 在不降低安全边界的前提下与规则路由打平，并在纯政策问题上减少不必要的客户数据访问；代价是每条平均多约 740 Token、1.6 秒。默认仍使用 rules，react 作为可切换模式保留。

## 局限

- 只在这份 100 条英文为主的 Baseline 上验证，规则已在同一数据集上调过，结果对 rules 有利。
- 只有一次运行，未测量模型输出的波动。
- 规则模式本次复测为 0.91，低于 2026-08-30 记录的 0.99；9 条失败均为 HITL 判定，原因尚未单独定位。
